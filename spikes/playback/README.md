# Spike (b): playback on Windows

**Question.** Does `just_audio`, through `just_audio_media_kit`, do what an audiobook needs on
Windows: a book made of several physical files, accurate resume into file N at offset T, playback
speed, and a position stream trustworthy enough to store progress from?

**Status: Windows complete. Android not run** — blocked on the emulator hypervisor driver, see
`spikes/quickjs_binding/README.md`.

**Verdict: the stack works, and it has two traps that would each silently corrupt resume.**
Neither is visible in the API surface or the documentation. Both must be encoded in the
`PlaybackEngine` adapter §6.1 puts in front of the engine, which is exactly the kind of thing that
interface exists for.

Versions: `just_audio` 0.10.6, `just_audio_media_kit` 2.1.0, `media_kit` 1.2.6,
`media_kit_libs_windows_audio` 1.0.9, on Flutter 3.47.3.

Test audio is generated by the probe as plain PCM sine tones. Nothing is downloaded and no real
audiobook is involved; generating it also means every duration is known exactly, which is what
makes the assertions meaningful. Volume is forced to zero so the probe can run unattended.

## What works

- **Duration probing on load is exact.** A 2.000 s file reports 2000 ms, delta 0 ms. §6.4 assumes
  durations are often unknown until probed; on Windows the probe is reliable.
- **Multi-file playlists work.** `setAudioSources` accepts the queue, reports the right length,
  and **advances across file boundaries unattended** — index went 0 → 1 at the boundary with
  per-item `duration` and `position` updating correctly. This is the §6 model of "queue items are
  physical files" and it holds.
- **Speed works.** 3.0 s of audio at 2.0x completed in 1392 ms of wall clock.
- **Pause holds position.** Paused at 821 ms, still 821 ms 300 ms later. Progress written on pause
  is trustworthy.
- **Position tracks wall clock closely** during playback: at t=2400 ms the reported position was
  2387 ms, a lag of about 15 ms.

## Trap 1: a combined seek silently discards the position

`seek(position, index: n)` moves to the requested index but **throws away the position** whenever
it crosses to a different index. It does not throw. It does not warn. The index is right, the
duration updates to the new item, and the offset is simply gone.

Measured, asking in every case for "index 1, offset 1500 ms":

| Recipe | Result |
|---|---|
| A. `seek(1500ms, index: 1)` while paused | **0 ms — position lost** |
| B. `seek(0, index: 1)` then `seek(1500ms)` | **1500 ms — correct** |
| C. `setAudioSources(..., initialIndex: 1, initialPosition: 1500ms)` | **1500 ms — correct** |
| D. play first, then `seek(1500ms, index: 1)` | **15 ms — position lost** |
| E. pause mid-file, read back 300 ms later | 821 ms then 821 ms — correct |

"Resume this book at file 2, 1500 ms in" is the single most important operation the engine
performs, and recipe A is the obvious way to write it. It fails silently, and it fails in the one
direction nobody tests: the user reopens a book and starts from the beginning of the wrong file.

**Rule for the adapter.** Never pass a position and an index to `seek` together. Use recipe C on a
cold start, when the queue is being loaded anyway, and recipe B when the queue is already loaded.

## Trap 2: position resets to zero on completion

When an item finishes, the position stream emits **0** as its final value and the `position`
getter reads 0 thereafter:

```
peak 2730ms, tail = [2670, 2688, 2703, 2719, 2730, 0], position after completed = 0ms
```

A progress store that listens to `positionStream` and writes what it receives — the obvious
implementation — **writes 0 at the end of every single file**. The user finishes a chapter, and
the app records that they never started it.

**Rule for the adapter.** Progress must never be written while `processingState` is `completed`,
and the value written should be the last position observed *before* completion, not the one after.
Completion is a signal to advance the Timeline, not a position sample.

## A third, smaller finding: the end-of-file shortfall varies

Playback stops short of the nominal duration by a variable margin — 90 ms in one run, 270 ms in
another, on the same 3.0 s file. "Finished" therefore cannot be defined as `position == duration`,
nor as any fixed epsilon that happens to work today. Use the `completed` state, or a generous
threshold, and treat the shortfall as noise rather than data.

## Two API rules the probe learned the hard way

Both cost a debugging cycle each and are worth writing down, since the adapter hits them too:

1. **`position` is not settled synchronously after `await seek(...)`.** The engine passes through
   `buffering` first. Read the position only after waiting for `ready`.
2. **`await play()` does not mean "play to completion".** It returned in about 1 ms in the first
   version of this probe and made four unrelated tests look broken. Start playback unawaited and
   wait on `processingState` instead.

## Not covered

`audio_service` and SMTC media controls, audio focus and interruptions, headphone and Bluetooth
route changes, background playback with the window closed, network sources with custom request
headers, gapless behaviour at a boundary as heard rather than as reported, and every one of these
on Android. The Android run in particular is not optional: `just_audio` uses ExoPlayer there, a
completely different backend, so **nothing measured here transfers**. Both traps above are
properties of the media_kit backend and may not exist on Android — or may exist differently.

## Reproducing

```
cd spikes/playback
flutter pub get
flutter build windows --debug
./build/windows/x64/runner/Debug/playback_probe.exe
```
