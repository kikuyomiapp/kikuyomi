# Spike (c): downloads on Windows

**Question.** Does `background_downloader` behave the way §5 needs — resumable transfers, progress
reporting, concurrency, and a sane story for URLs that expire between the moment a book is queued
and the moment its bytes are fetched?

**Status: Windows complete, 7 of 7 probes pass. Android not run**, and that is where most of the
difficulty lives.

The probe runs **its own HTTP server on localhost**. That is deliberate: expiry, range support and
failure modes become exact and repeatable instead of depending on someone else's server, and the
spike downloads nothing from the internet. The payload is a generated byte pattern, so a truncated
or mis-assembled file is detectable rather than merely the wrong length.

## Results

```
[PASS] plain download completes and is byte-exact      3145728 bytes
[PASS] progress callback fires with intermediate values 6 updates, last 1.00
[PASS] expired URL fails cleanly without a partial file status=failed, no file left behind
[PASS] re-fetch after the link is valid again succeeds  origin saw 2 requests
[PASS] pause and resume, resulting file intact          resumed, 3145728 bytes byte-exact
[PASS] four concurrent downloads all complete           4 files, all full size
[PASS] 404 fails without leaving a file                 status=notFound

origin request counts: {/file: 5, /slow: 3, /expiring: 2, /missing: 1}
```

The behaviours §5 depends on all hold on Windows:

- **Pause is real, not a cancel.** The transfer resumed with a `Range` request — visible as the
  third hit on `/slow` — and the reassembled file was byte-exact against the expected pattern. A
  book of many large files can therefore be paused without losing work.
- **Failures leave no file behind.** Both the expired link (403) and the missing resource (404)
  failed without creating a partial or empty file. That matters more than it sounds: an empty file
  that looks like a finished download is how a library ends up with silent, unplayable entries.
- **Re-fetching after expiry is unremarkable.** The same logical item fetched again once the link
  was valid simply worked, which is the shape the queue needs — the queue entry survives and only
  the URL changes.
- **Concurrency works**, so the per-source limits §5 wants are a policy decision rather than a
  capability question.

## The trap: `progress` is not a number between 0 and 1

The pause probe reported "paused at -500%". That is not a probe bug. `progress` is a union of a
fraction and five negative sentinels:

```dart
const progressRunning        =  0.0;
const progressComplete       =  1.0;
const progressFailed         = -1.0;
const progressCanceled       = -2.0;
const progressNotFound       = -3.0;
const progressWaitingToRetry = -4.0;
const progressPaused         = -5.0;
```

A progress bar bound directly to this value renders nonsense the moment anything goes wrong, and
"anything goes wrong" includes the ordinary case of the user pressing pause. Worse, code that
averages progress across a book's files to show one bar per book will produce a number that is
quietly wrong rather than obviously broken, because one paused file drags the mean below zero.

**Rule for the transport adapter:** never pass `progress` through to the UI. Map it to a sealed
state — running with a fraction, paused, retrying, failed — at the boundary, and let the UI switch
on that. This is the same shape of finding as the two in spike (b), and the same answer: the
adapter exists to stop a package's quirks leaking into features.

## What Windows cannot tell us

Most of what makes §5 hard is not observable here, and none of the above should be read as
evidence about Android:

- **Foreground-service limits.** Android will kill background work, and the rules differ by
  manufacturer. This is the single biggest unknown in the download subsystem.
- **Process death mid-transfer**, and whether the queue and partial files survive it.
- **Battery optimisation** and Doze, which decide whether a download queued overnight is there in
  the morning.
- **iOS suspension.** Appendix A notes that extension code cannot run while the app is suspended,
  so an expired URL cannot be re-resolved until the app is next opened. No library changes that;
  the UI has to be honest about it.
- **Real network conditions**: a localhost origin never times out, never resets a connection, and
  never returns a truncated body.

## Not covered

Servers that do not support `Range` (the `/norange` endpoint exists but is unused), retry and
backoff policy, per-source concurrency limiting, storage accounting and the out-of-space case,
notifications, and downloads of a size that actually stresses the disk.
